# 展示格式

有对应 MCP App 且宿主支持时优先展示 UI，聊天只补结论和警告。用户只要文字时遵从。没有 App 的工具用可读文字，不把「工具可供 App 调用」误认为它自带界面，也不把 UI 打开成功当作数据已核实。

## 通用规则

- 第一屏是结论。每个事实全文只写一次，后面需要时用简称引用。用户说「展开」「详细」「看证据」时，再用对应证据工具展开具体结论。
- 关键事实后附短来源：来源名 · 发布日期。采集或核验时间只在影响时效判断时写。有冲突时并列写出，没有冲突不写「无冲突」。
- [证据边界](evidence-limits.md)里的同类限定在结尾合并成一行「限制：…」，不在每条线索后重复。
- 关键警告、准备限制和必要问题压缩成短句保留，不删除。系统警告放在限制行，不改写成要向客户追问的问题。
- 没有内容的部分不展开，也不为凑模板生成空章节。
- 不展示 operation_id、run_id、各类内部 ID、哈希和原始字段名。错误用业务语言说明含义，不猜测原因；错误码只在用户要求或排障时给。

## 各类输出

**基础画像**，约 300 字。
- 一行写确认的主体：法定名称和信用代码。
- 行业标签、规模和经营线索合计不超过 3 条。
- 缺口一行。

**研究成果**，约 800 字。
- 头部一行：企业 · 研究日期 · 完成或部分完成。
- 优先跟进的 1–2 个产品，每个写机会等级和置信度、最多两条有证据的理由、主要阻碍、一个待核实问题。
- 其余产品各一行「产品 等级/置信度：一句话」。没有覆盖的产品合并为一行。
- 产品专题的新购、替换、补充三条路径各一行，写状态和依据。有反证时同行写出，不能只报「值得探索」。
- 结尾写一行覆盖与限制。

**首次拜访简报**，约 1000 字。
- 开头用两行写简要结论。
- 七节按原标题保留，每节最多 3 条。没有内容的节合并为一行「暂无：…」。
- 切入假设、现场问题、人员与岗位三节标为待验证的建议。
- 人员与岗位节：在节标题标注一次「公开资料，未经核实」；专利署名每人保留公开号和公开日期，链接放到证据展开；与有独立任职证据的图谱人员分开写。
- 现场问题突出 3–5 个，其余必要问题放在「更多问题」一行。
- 准备限制一行。

**客户开发简报**，约 600 字。按开发判断、内部资源、关键线索、下一步、资料限制的顺序，每部分最多 3 行，有内容才写。

**关键人**。
- 按决策层、技术负责人、研发骨干分组，在组标题标注一次「未经核实」。
- 每人一行：姓名 · 职务或线索 · 来源和日期。`likely_lead` 写作「可能骨干」。
- 无具名人员的方向和招聘信号合并为一行。

**单产品比较**。
- 排名表列：名次、企业、机会、置信度、时机、主要阻碍。并列名次保留。企业用名称，同名需要区分时附信用代码，不用信用代码解释优先级。
- needs_research 合并为一行，写企业和原因。
- 联系快照一行，写完整性和警告。

**定向追问**。答案先行，三句以内。按「资料直接支持 / 可能解释 / 仍需核实 / 未回答」分类，只写有内容的类别。
